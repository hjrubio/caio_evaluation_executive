paragraph:75 :: Anexo C · Arquitectura técnica y modelos
paragraph:76 :: Ningún modelo generativo decide solo: el LLM captura, un modelo de ML explicable predice, Jev decide dentro de un conjunto cerrado de opciones tipadas y un motor de reglas versionadas puede anular la decisión antes y después.
paragraph:77 :: Cuatro capas sobre los sistemas actuales
paragraph:78 :: La plataforma se monta sobre el FSM actual: lee y escribe órdenes por API, sin reemplazar el core.
paragraph:79 :: Flujo de decisión del triage
paragraph:80 :: Captura. El agente conversacional (LLM) pregunta y devuelve un JSON validado contra un esquema tipado: síntoma, servicio afectado, equipo, desde cuándo, disponibilidad. Si el JSON no valida, repregunta; al segundo fallo deriva a una persona. El agente no ejecuta acciones.
paragraph:81 :: Predicción. Un modelo de ML (gradient boosting) entrenado con datos propios estima la falla probable y la probabilidad de resolver a distancia. Variables: telemetría del equipo (potencia óptica, reinicios, errores), incidentes de red abiertos en la zona, historial de órdenes del cliente y antigüedad del equipo. Cada predicción viaja con su explicación (valores SHAP de las 5 variables principales).
paragraph:82 :: Decisión. Jev (TypeSafe AI) elige una opción del enum tipado. El tipo no permite opciones fuera del conjunto ni un despacho sin ventana ni skill. Respaldo: Decisions API de OpenAI con el mismo esquema; si fallan ambos proveedores, decide la combinación ML + reglas.
paragraph:83 :: Control. El motor de reglas versionadas, de las que es dueño Operaciones, actúa dos veces. Antes: resuelve los casos obvios sin consultar a la IA (por ejemplo, una caída masiva conocida implica aviso y no despacho). Después: puede anular la decisión (por ejemplo, un cliente con 2 reclamos en 30 días va siempre a visita o a una persona).
paragraph:84 :: Acción. Se ejecuta la opción, se informa al cliente y todo queda registrado.
paragraph:85 :: Opciones tipadas
paragraph:86 :: type DecisionTriage =
  | { opcion: "SIN_ACCION"; motivo: "FALLA_MASIVA_CONOCIDA" | "RESUELTO_POR_CLIENTE" }
  | { opcion: "GUIA_REMOTA"; procedimiento: IdProcedimiento; maxMinutos: 15 }
  | { opcion: "ACCION_REMOTA_RED"; accion: "REINICIO" | "RECONFIGURACION" | "CAMBIO_PERFIL" }
  | { opcion: "DESPACHO"; skill: Skill; prioridad: 1 | 2 | 3; ventana: Ventana20Min }
  | { opcion: "DERIVAR_PERSONA"; motivo: MotivoDerivacion }
paragraph:87 :: Ningún otro valor compila. Una compensación al cliente no es una opción del triage: la decide una persona según la política del anexo E.
paragraph:88 :: Trazabilidad de Jev
paragraph:89 :: Cada decisión genera un registro inmutable (append-only, con hash encadenado) en el data lake.
paragraph:90 :: Retención de 3 años. Lo consultan el CISO, Legales y Auditoría Interna, y responde a cualquier reclamo del tipo "¿por qué no me mandaron un técnico?".
paragraph:91 :: Modelo de datos unificado
paragraph:92 :: MLOps y operación
paragraph:93 :: Entornos: desarrollo, pruebas y producción separados; datos de producción seudonimizados en desarrollo.
paragraph:94 :: Modo sombra: el triage corre en Q1 sin actuar; sus decisiones se comparan con lo que pasó.
paragraph:95 :: Reentrenamiento: mensual para el modelo de falla, con aprobación del comité si cambia la métrica en más de 2 pp.
paragraph:96 :: Monitoreo: deriva de datos, tasa de anulación por reglas, latencia y costo por decisión; alerta si las anulaciones superan el 15%.
paragraph:97 :: Conmutación: el gateway cambia de proveedor ante una falla; ML + reglas como último respaldo.
paragraph:98 :: Anexo D · Gobierno y autonomía
paragraph:99 :: La IA solo actúa sola en tareas de bajo riesgo y reversibles. Todo lo que afecta a un empleado o cierra un caso sin confirmación del cliente lo decide siempre una persona. El comité de IA decide en cada gate trimestral y el CISO tiene veto.

paragraph:101 :: Subir un caso de nivel exige aprobación del comité, 8 semanas de evidencia contra el grupo de control y la firma del CISO. Bajarlo lo puede hacer el COO solo, en cualquier momento.

paragraph:110 :: Anexo E · Seguridad, legal y Ley 25.326
paragraph:111 :: Todo ahorro se mide contra un grupo de control permanente del 10%. A los proveedores de IA solo viaja el estado del caso, nunca datos personales. El plan cumple la Ley 25.326 y el Convenio 108+, vigente en Argentina por la Ley 27.699, con evaluación de impacto firmada por el CISO antes de cada salida a producción.
paragraph:112 :: Grupo de control permanente del 10%
paragraph:113 :: Qué es: el 10% de los reclamos elegibles sigue el proceso actual, sin triage ni despacho por IA. La asignación es aleatoria y estable por cliente (hash del ID).
paragraph:114 :: Para qué: el uplift de cada palanca es la diferencia entre tratados y control en visitas por orden resuelta, first-time fix, visitas fallidas, NPS post-visita y SLA. Es la evidencia que pide el CFO y la base del gate de Q2.
paragraph:115 :: Despacho y ruteo: como afectan a toda una agenda, se controlan por zona y semana alternadas durante el piloto de Q3.
paragraph:116 :: Duración: permanente; el comité puede bajarlo al 5% desde 2029 si la diferencia es estable durante 4 trimestres.
paragraph:117 :: Costo: ya descontado del beneficio del anexo B.
paragraph:118 :: Controles clave
paragraph:119 :: Ley 25.326 y Convenio 108+
paragraph:120 :: Política de resolución remota y compensaciones
paragraph:121 :: Resolución remota: la IA puede guiar al cliente hasta 15 minutos; si no se resuelve, se ofrece visita sin volver a preguntar.
paragraph:122 :: Derecho a visita: un cliente que pide técnico lo recibe, aunque la IA haya estimado resolución remota.
paragraph:123 :: Compensaciones: las bonificaciones por falla repetida siguen la tabla vigente de Atención al Cliente. Hasta 1 mes de abono, decide el representante; por encima, el supervisor. La IA nunca promete ni otorga una compensación.
paragraph:124 :: Registro: toda compensación queda vinculada a la orden y a la decisión de Jev.
paragraph:125 :: Versionado: Operaciones es dueño de las reglas y Atención al Cliente de la tabla de compensaciones; cada cambio queda versionado y lo informa el comité.
paragraph:126 :: Seguridad técnica
paragraph:127 :: Autenticación: SSO con doble factor para consolas y app del técnico; validación del cliente por número de línea más un dato del contrato.
paragraph:128 :: Autorización: roles mínimos; los contratistas solo ven sus órdenes.
paragraph:129 :: Cifrado: en tránsito (TLS 1.2+) y en reposo; claves gestionadas por Seguridad.
paragraph:130 :: DLP: filtros sobre salidas del gateway y del copiloto para bloquear PII y datos de red sensibles.
paragraph:131 :: Pruebas: red teaming del agente antes del gate de Q1 y antes de cada nueva capacidad.
